# PR0301: Despliegue automatizado de servidor web mediante User Data y metadatos IMDSv2

## 1. Fundamentos teóricos

### ¿Qué es el *User Data* en Amazon EC2?

Cuando se aprovisiona una máquina virtual en la nube, la configuración manual por SSH es ineficiente y no escala. AWS EC2 permite pasar instrucciones de arranque mediante el parámetro **User Data**.

El **mecanismo subyacente** en distribuciones Linux es `cloud-init`, que es el software responsable de procesar este parámetro. Por defecto, los scripts pasados en *User Data* se ejecutan con privilegios de superusuario (`root`) **únicamente durante el primer arranque de la instancia** (en la fase final del proceso de inicialización del sistema operativo). Reiniciar la máquina no vuelve a disparar el script a menos que se reconfigure `cloud-init`.

Todo lo que imprima el script (salida estándar y errores) queda registrado en el archivo local `/var/log/cloud-init-output.log` Este log es la herramienta principal de resolución de incidencias (*troubleshooting*) si el servidor web no responde tras el despliegue.


### El servicio de metadatos de instancia (IMDS)

El **Instance Metadata Service (IMDS)** es una API interna que AWS expone a cada máquina virtual para que el sistema operativo pueda inspeccionar su propio contexto de ejecución sin requerir credenciales ni llamadas a la API externa de AWS. A través de este servicio, una instancia puede conocer su propio identificador (`instance-id`), el tipo de máquina, la subred, la zona de disponibilidad en la que está arrancada o las credenciales temporales del rol IAM que tenga asignado.

El servicio responde exclusivamente en la dirección IPv4 reservada **`169.254.169.254`**, perteneciente al rango de enlace local (*link-local*, RFC 3927). Esta dirección tiene una particularidad de diseño fundamental a nivel de redes: **el tráfico nunca sale del host físico ni se enruta a través de pasarelas o Internet**.

Cuando el sistema operativo emite un paquete hacia esa IP, la tarjeta de red virtual y el hipervisor de AWS (el sistema Nitro o Xen) interceptan la trama directamente en la capa de virtualización y responden de forma local. Gracias a esto, el servicio funciona de inmediato, sin necesidad de configuración DNS, sin tabla de rutas hacia el exterior e incluso en instancias aisladas dentro de subredes privadas sin acceso a Internet.


### Grupos de Seguridad (*Security Groups*)

Un *Security Group* actúa como un **cortafuegos virtual con estado** a nivel de interfaz de red elástica (ENI). **Con estado** o *stateful* quiere decir que si se autoriza el tráfico de entrada en el puerto 80, la respuesta saliente hacia el cliente se permite automáticamente, sin necesidad de definir una regla explícita en la tabla de salida. Por defecto, todo el tráfico entrante que no coincida explícitamente con una regla de entrada (*Inbound rule*) es bloqueado.



## 2. Objetivos de la práctica

Los objetivos de esta práctica son los siguientes:

1. Configurar un Grupo de Seguridad adaptado a un servicio web público y administración remota.
2. Diseñar un script Bash de inicialización (*User Data*) compatible con Amazon Linux 2023.
3. Consultar programáticamente metadatos de la instancia utilizando el protocolo **IMDSv2**.
4. Generar dinámicamente un panel HTML que refleje la topología y datos de la máquina.
5. Analizar los registros del sistema para diagnosticar el ciclo de arranque automatizado.


## 3. Guía de pasos a realizar

### Paso 1: Creación del Grupo de Seguridad (*Security Group*)

Antes de lanzar el cómputo, se deben definir las políticas de filtrado de tráfico.

1. En la consola de AWS, acceder a **EC2** > **Network & Security** > **Security Groups**.
2. Pulsar en **Create security group** y rellenar los datos:
  - **Security group name:** `sg-servidor-web-asir`
  - **Description:** `Permitir acceso HTTP publico y SSH desde el aula`
  - **VPC:** Seleccionar la VPC por defecto del laboratorio.

3. Configurar las reglas de entrada (**Inbound rules**):

| Tipo     | Protocolo | Puerto | Origen (*Source*)           | Descripción                    |
| -------- | --------- | ------ | --------------------------- | ------------------------------ |
| **SSH**  | TCP       | 22     | IP pública del aula         | Gestión remota segura          |
| **HTTP** | TCP       | 80     | Anywhere-IPv4 (`0.0.0.0/0`) | Acceso público al servicio web |

4. Dejar las reglas de salida (**Outbound rules**) por defecto (todo el tráfico permitido hacia `0.0.0.0/0`) para que la máquina pueda descargar paquetes del repositorio oficial de AWS.
5. Guardar pulsando en **Create security group**.


### Paso 2: Análisis del Script de User Data

El siguiente script se inyectará en la instancia durante el asistente de lanzamiento.

```bash
#!/bin/bash
# -----------------------------------------------------------------
# 1. Actualización e instalación del servidor web Apache
# -----------------------------------------------------------------
dnf update -y
dnf install -y httpd

# Habilitar e iniciar el servicio en el arranque de systemd
systemctl enable httpd
systemctl start httpd

# -----------------------------------------------------------------
# 2. Obtención de metadatos mediante IMDSv2
# -----------------------------------------------------------------
# Paso A: Generar token de sesión válido por 6 horas (21600 segundos)
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# Paso B: Consultar metadatos usando el token en la cabecera HTTP
INSTANCE_ID=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-id)

INSTANCE_TYPE=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-type)

AVAILABILITY_ZONE=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/placement/availability-zone)

PRIVATE_IP=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/local-ipv4)

# -----------------------------------------------------------------
# 3. Creación del archivo index.html dinámico
# -----------------------------------------------------------------
cat <<EOF > /var/www/html/index.html
<!DOCTYPE html>
<html lang="es">
<head>
    <meta charset="UTF-8">
    <title>Servidor Web EC2 - ASIR Cloud</title>
    <style>
        body { font-family: 'Segoe UI', Tahoma, Geneva, Verdana, sans-serif; background-color: #f4f6f9; margin: 40px; color: #333; }
        .card { background: white; max-width: 650px; margin: 0 auto; padding: 25px; border-radius: 8px; box-shadow: 0 4px 6px rgba(0,0,0,0.1); border-top: 5px solid #FF9900; }
        h1 { color: #232F3E; font-size: 24px; margin-bottom: 20px; }
        table { width: 100%; border-collapse: collapse; margin-top: 15px; }
        th, td { text-align: left; padding: 12px; border-bottom: 1px solid #e1e4e8; }
        th { background-color: #f8f9fa; color: #555; }
        .badge { background: #e8f5e9; color: #2e7d32; padding: 4px 8px; border-radius: 4px; font-weight: bold; font-family: monospace; }
    </style>
</head>
<body>
    <div class="card">
        <h1>Servidor Web Aprovisionado con User Data</h1>
        <p>Estado del servicio: <span class="badge">ACTIVO (HTTPD)</span></p>
        <table>
            <tr><th>Parámetro</th><th>Valor consultado (IMDSv2)</th></tr>
            <tr><td><strong>ID de la Instancia</strong></td><td>$INSTANCE_ID</td></tr>
            <tr><td><strong>Tipo de Instancia</strong></td><td>$INSTANCE_TYPE</td></tr>
            <tr><td><strong>Zona de Disponibilidad (AZ)</strong></td><td>$AVAILABILITY_ZONE</td></tr>
            <tr><td><strong>Dirección IP Privada</strong></td><td>$PRIVATE_IP</td></tr>
        </table>
    </div>
</body>
</html>
EOF

```


### Paso 3: Lanzamiento de la Instancia EC2

1. Ir a **EC2** > **Instances** > **Launch Instances**.
2. **Name and tags:** Asignar el nombre `web-server-{iniciales}-01`.
3. **Application and OS Images (Amazon Machine Image):** Seleccionar **Amazon Linux 2023 AMI** (arquitectura x86_64).
4. **Instance type:** Seleccionar `t2.micro` o `t3.micro`
5. **Key pair (login):** Crear una clave personal `.pem` para acceder por terminal.
6. **Network settings:**
   - Pulsar en **Edit**.
   - **VPC:** VPC por defecto.
   - **Auto-assign public IP:** asegurarse de que esté en **Enable**.
   - **Firewall (security groups):** seleccionar **Select existing security group** y marcar `sg-servidor-web-asir`.
7. **Advanced details:**
  - Desplegar la sección inferior.
  - **Metadata version:** comprobar que esté seleccionado **V2 only (token required)** o *V1 and V2 (token optional)*. Para forzar buenas prácticas, fijarlo en **V2 only**.
  - Localizar el cuadro de texto **User data** al final de la página y pegar el script completo del **Paso 2**.
8. Pulsar en **Launch instance**.


### Paso 4: Verificación y resolución de problemas

#### 1. Comprobación vía navegador web

1. En la lista de instancias, esperar a que el estado pase a `Running` y los dos chequeos de estado indiquen `2/2 checks passed`.
2. Copiar la **Public IPv4 address** o la **Public IPv4 DNS**.
3. Abrir una pestaña en el navegador y acceder por HTTP (Asegurate de que el navegador no redirija automáticamente a `https://`, ya que el puerto 443 no está configurado).

#### 2. Inspección del log del sistema por SSH

Para verificar el comportamiento de `cloud-init` y cómo se procesó el script:

1. Conectarse a la máquina mediante SSH:
  ```bash
  ssh -i "clave_privada.pem" ec2-user@<TU_IP_PUBLICA>
  ```
2. Inspeccionar el registro de salida de arranque:
  ```bash
  sudo cat /var/log/cloud-init-output.log
  ```
3. Comprobar manualmente la consulta a IMDSv2 desde la propia terminal:
  ```bash
  # Obtener el token
  TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 60")

  # Consultar el AMI ID utilizado para lanzar la máquina
  curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/ami-id
  echo ""
  ```
