# PR0305. Cómputo orientado a eventos con AWS Lambda y Amazon S3

## 1. Fundamentos teóricos (Apuntes de referencia)

### Del modelo basado en servidores al paradigma Serverless (FaaS)

En las prácticas anteriores hemos transitado desde la infraestructura tradicional de máquinas virtuales (IaaS con EC2) hasta la abstracción de contenedores sin servidor (CaaS con Fargate). Sin embargo, en ambos modelos existe un principio subyacente común: **los recursos de cómputo se pagan y se mantienen en ejecución de forma continua**, independientemente de si están procesando peticiones o se encuentran inactivos.

El paradigma **Serverless (Sin servidor)** y, en particular, el modelo **FaaS (*Function as a Service*)** rompe con este esquema. Con servicios como **AWS Lambda**, el código ya no reside en un servidor en estado de escucha permanente (*daemon*). En su lugar, el código se despliega como una función independiente alojada en un entorno gestionado por AWS.

El ciclo de vida de una función FaaS se rige exclusivamente por eventos:

1. **Inactividad absoluta ($0 de coste y cero recursos consumidos):** si la función no recibe peticiones, no hay contenedores ni microinstancias corriendo.
2. **Activación instantánea (*Cold Start*):** cuando se produce un evento que desencadena la función, la plataforma aprovisiona de forma transparente un entorno de ejecución en milisegundos, carga el código y procesa el evento.
3. **Escalado concurrente automático:** si se producen 1.000 eventos simultáneos, AWS Lambda despliega automáticamente 1.000 entornos aislados en paralelo para procesar cada carga de forma independiente, reduciendo la ejecución a cero una vez finalizado el trabajo.


### Arquitecturas orientadas a eventos (*Event-Driven Architectures*)

En los sistemas distribuidos modernos, la comunicación directa sincrónica (como llamadas HTTP REST directas entre servicios) crea acoplamientos rígidos donde la caída de un componente afecta a toda la cadena. Las **Arquitecturas Orientadas a Eventos** desacoplan los sistemas mediante productores, intermediarios y consumidores asíncronos.

En esta práctica, el flujo se basa en el almacenamiento de objetos de **Amazon S3**:

- **El Productor:** un usuario o aplicación que sube un archivo (por ejemplo, un registro de texto o un log) a un bucket de S3.
- **El Evento:** Amazon S3 genera de manera nativa un evento interno (notificación `s3:ObjectCreated:*`) cada vez que un objeto se almacena con éxito.
- **El Consumidor (*Trigger*):** el servicio AWS Lambda se suscribe a dicho evento, interceptando la notificación en tiempo real y recibiendo un objeto JSON estructurado con los metadatos exactos de la acción (nombre del bucket, clave del archivo, tamaño y marca temporal).


### Seguridad en entornos Serverless y el rol `LabRole`

Al trabajar con funciones Lambda que interactúan con otros servicios de AWS (como leer un archivo de un bucket S3 o escribir registros en CloudWatch), la función necesita permisos de seguridad explícitos definidos mediante un **Rol de Ejecución IAM (*Execution Role*)**.

En un entorno corporativo estándar, el administrador de sistemas diseña políticas de mínimo privilegio que otorgan únicamente acceso de lectura sobre el bucket específico. Sin embargo, debido a las restricciones de gestión de identidad del **AWS Academy Learner Lab**, los alumnos no pueden crear nuevos roles IAM ni modificar políticas de confianza. Por ello, todas las funciones Lambda creadas en este laboratorio deben asociarse obligatoriamente al rol preexistente denominado **`LabRole`**, el cual ya incluye los permisos necesarios para interactuar con S3, Lambda y CloudWatch.



## 2. Objetivos de la práctica

1. Comprender el modelo de ejecución *Serverless* mediante **AWS FaaS (AWS Lambda)** y su tarificación por eventos.

## 3. Guía paso a paso

### Paso 1: Creación del Bucket S3 para la ingesta de archivos

1. En la consola de AWS, buscar y acceder al servicio **S3**.
2. Hacer clic en **Create bucket**.
3. **General configuration:**
    - **Bucket name:** `bucket-procesador-asir-<tu-nombre-o-id>` (debe ser globalmente único).
    - **AWS Region:** seleccionar la misma región de trabajo (ej. `us-east-1`).
4. **Object Ownership:** mantener habilitado *ACLs disabled (recommended)*.
5. **Block Public Access settings for this bucket:** dejar marcada la opción por defecto *Block all public access* (las comunicaciones entre S3 y Lambda se realizan de forma interna y segura mediante APIs de AWS, sin requerir exposición pública).
6. Pulsar en **Create bucket**.


### Paso 2: Creación de la función AWS Lambda

1. En la consola de AWS, buscar y acceder al servicio **Lambda**.
2. Hacer clic en **Create function**.
3. Seleccionar **Author from scratch** (Crear desde cero).
4. **Basic information:**
    - **Function name:** `funcion-procesadora-s3`.
    - **Runtime:** `Python 3.11` (o superior).
    - **Architecture:** `x86_64`.
5. **Permissions (Restricción crítica de AWS Academy):**
    - Desplegar la sección **Change default execution role**.
    - Seleccionar **Use an existing role**.
    - En el desplegable *Existing role*, elegir estrictamente el rol **`LabRole`**.
6. Pulsar en **Create function**. Una vez creada la función, aparecerá el entorno de desarrollo integrado (*Code source*). Reemplazar el código por defecto del archivo `lambda_function.py` por el siguiente script:

```python
import json
import urllib.parse
import boto3

# Inicializar el cliente de S3 mediante el SDK Boto3
s3_client = boto3.client('s3')

def lambda_handler(event, context):
    print("--- INICIO DEL PROCESAMIENTO DE EVENTO S3 ---")
    
    # 1. Extraer los datos del evento JSON enviado por S3
    try:
        bucket_name = event['Records'][0]['s3']['bucket']['name']
        file_key = urllib.parse.unquote_plus(event['Records'][0]['s3']['object']['key'], encoding='utf-8')
        file_size = event['Records'][0]['s3']['object'].get('size', 0)
    except Exception as e:
        print(f"Error al extraer metadatos del evento: {e}")
        raise e

    print(f"Archivo detectado: {file_key} en el bucket: {bucket_name} (Tamaño: {file_size} bytes)")

    # 2. Leer el contenido del archivo directamente desde S3
    try:
        response = s3_client.get_object(Bucket=bucket_name, Key=file_key)
        file_content = response['Body'].read().decode('utf-8')
        
        print("--- CONTENIDO DEL ARCHIVO RECUPERADO ---")
        print(file_content)
        print("----------------------------------------")
        
        # Procesamiento básico: contar líneas y palabras
        lines = file_content.splitlines()
        num_lines = len(lines)
        num_words = sum(len(line.split()) for line in lines)
        
        print(f"Estadísticas del archivo -> Líneas: {num_lines} | Palabras: {num_words}")

    except Exception as e:
        print(f"Error al leer el objeto {file_key} desde el bucket {bucket_name}: {e}")
        raise e

    return {
        'statusCode': 200,
        'body': json.dumps(f"Archivo {file_key} procesado correctamente por AWS Lambda.")
    }
```

7. Hacer clic en el botón superior **Deploy** para guardar y compilar los cambios del código.



### Paso 3: Configuración del disparador (*Trigger*) de S3

Para que S3 invoque automáticamente la función Lambda ante cada subida de archivos, se debe configurar un enlace nativo:

1. En la consola de la función Lambda (`funcion-procesadora-s3`), localizar la sección superior (*Function overview*).
2. Pulsar en el botón **Add trigger**.
3. Configurar los parámetros del disparador:
    - **Source:** seleccionar **S3**.
    - **Bucket:** seleccionar el bucket creado en el Paso 1 (`bucket-procesador-asir-...`).
    - **Event type:** marcar **All object create events** (`s3:ObjectCreated:*`).
    - **Recursive invocation:** marcar la casilla de reconocimiento de advertencia para prevenir bucles de recursividad (exigido por AWS).
4. Pulsar en **Add**.


### Paso 4: Creación de archivo de prueba y validación del flujo

1. Crear un archivo de texto plano en el equipo local denominado `muestra-servidores.txt` con el siguiente contenido de ejemplo:
   
    ```text
    Informe de auditoria de sistemas ASIR
    Servidor 1: Operativo en zona us-east-1a
    Servidor 2: Operativo en zona us-east-1b
    Base de datos: Sincronizada y sin errores criticos
    ```

2. Volver a la consola de **Amazon S3**, entrar dentro del bucket creado e hacer clic en **Upload**.
3. Seleccionar el archivo `muestra-servidores.txt` y pulsar en **Upload**.
4. Una vez completada la subida con éxito, el evento de S3 se habrá disparado de forma instantánea.



### Paso 5: Inspección de resultados en CloudWatch Logs

1. Regresar a la consola de **AWS Lambda** > función `funcion-procesadora-s3`.
2. Seleccionar la pestaña **Monitor** y hacer clic en **View logs in CloudWatch**.
3. Se abrirá el flujo de registros (*Log streams*). Hacer clic sobre el flujo más reciente generado por la ejecución.
4. Inspeccionar las líneas impresas por el script (salida estándar `print`):
    - Se observará el nombre del bucket y la clave del archivo capturados dinámicamente desde el JSON del evento.
    - Se visualizará el contenido completo del archivo de texto leído mediante la API de Boto3.
    - Se comprobará el cálculo del número de líneas y palabras procesadas sin haber desplegado ningún servidor virtual intermedio.
